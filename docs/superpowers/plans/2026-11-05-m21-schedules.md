**Goal.** An agent can have schedules. A schedule is a prompt that runs on a schedule as a new chat of that agent. Its result is saved as an AI Chat object in the space and announced with a notification. Schedules are made on the agent page or by the agent itself through a `schedule_manage` tool. Each one belongs to one space and runs only while that space is open; missed runs are offered by M14's catch-up on the next open. Schedule runs skip background reviews, and the curator never touches a skill a schedule uses.

**Architecture.** A schedule **is an M14 rule**: a `schedule` trigger plus one new action kind, `runAgent` (see "Our calls" 1 for why). The rule file is in the space's `.object/automations/<id>.json`, written through M14's store and routes, so the scheduler, its state file, the catch-up, the run log, the Trash and the watcher all apply unchanged. The new pieces:

- `automations_model.py` gains `RunAgentAction` and its shape rules.
- `automations.py` validates `runAgent` against the agent registry and hands each due occurrence to an agent job queue instead of running it on the scheduler thread.
- `schedulerun.py` holds `AgentJobs`, one worker thread per open space. It runs one job at a time as a headless agent chat through M20's `headless.run_chat` (M17's `agentrun.build_run` and M10's `ai.run_turn`) with `purpose="schedule"`, which isn't in M18's `reviews.REVIEW_PURPOSES`, so no review starts. `run_chat` writes the transcript; `schedulerun` saves the AI Chat object and sends the notification.
- `agentschedules.py` holds the helpers: the agent-facing schedule shape, and a machine-wide index in the state dir (`<state>/agent-schedules.json`). The curator asks that index which skills schedules use, for spaces that aren't open too.
- `api_schedules_v1.py` and `agent_tools_schedules.py` back the agent tool `schedule_manage`.
- The front end gets a **Schedules** tab on the agent page (`frontend/src/agents/SchedulesTab.tsx`, `ScheduleDialog.tsx`, `scheduleModel.ts`). Settings > Automations shows agent schedules as rows that open the same dialog.

**Tech Stack.** Python 3 (FastAPI, pydantic, the `mcp` server lib, httpx to loopback only), `uv`; React, TypeScript, zustand, shadcn/ui, Tailwind, vitest. Claude Code CLI **2.1.317** (`claude --version`). M21 adds **no CLI flag**: every run is built by M17's `agentrun.build_run` with M17's checked `CLI_FLAGS`.

**Spec.** `docs/superpowers/specs/2026-11-05-agents-design.md`, **section 9** (Schedules), plus the parts of other sections it names:

## Global Constraints

- Agents run only through the `claude` CLI under Gene's own login. Object never reads `~/.claude/.credentials.json` or any Claude token and never calls Anthropic's API. A schedule run is one `claude -p` run built by `agentrun.build_run`. No network client in `agentschedules`, `schedulerun` or `api_schedules_v1`; `agent_tools_schedules` uses `mcp_server.ObjectClient` to the loopback app only.
- The server binds `127.0.0.1` only. A schedule run's `OBJECT_API_URL` is the app's own loopback URL.
- **Fidelity to M14.** A schedule is stored with M14's rules, in that space's `.object/automations/`, with the agent's id. Its trigger is an M14 `schedule` (M8 repeat text by due date, `HH:mm` in `space.tz`, a `start` day). It gets M14's catch-up rules unchanged:
  - missed runs are never run without the user's answer;
  - the newest 50 are kept;
  - a gap of more than 10 minutes while running becomes a catch-up;
  - a new, re-enabled or rescheduled rule owes nothing;
  - each occurrence runs at most once.
- Runs happen **only while the schedule's space is open**: the jobs live in that space's app and stop with it.
- The agent stays machine-wide. Agent folders, `agent.json` and the registry hold no schedule.
- A run is **a new chat of the agent**. It uses the agent's soul, memory snapshot, skills, tools and switches, exactly as an interactive chat with that agent. It is kept as a transcript in the agent's `sessions/` and saved as an **AI Chat object** in the space with the Agent property, whatever the chat panel's save habit. It is announced with **a notification**, which obeys "Activate notifications" as M14's `notify` does.
- **Schedule runs skip background reviews** (spec section 9). No memory or skill review starts after a schedule run, and a schedule run doesn't move the review counters.
- **The curator never touches a skill a schedule uses** (spec section 5). This covers schedules in every space, open or not.
- The agent acts directly, as in a chat: write tools on, a read-write turn token named after the agent, writes announced `api:<agent name>` and kept in the activity log (M17).
- "Exclude from AI" keeps its promise. A run gets M17's fence and Object's tools unchanged.
- Everything is unlocked: no limit on the number of schedules, no badge, no gate.
- **Never write on read.**
  - Opening a space, listing rules or agents, or opening the Schedules tab writes no `.md` file.
  - The state dir's files (M14's state file, run logs, `agent-schedules.json`) are written only when their content changes, and only when there are schedules to record or old entries to drop.
- File safety:
  - Rule files go through M14's `JsonStore`: atomic, revision-checked, unknown keys kept.
  - The AI Chat object is made by `Space.create_object` and `save_body`, as M10's save does.
  - Deleting a schedule moves its rule to the space's Trash (restorable).
  - `agent-schedules.json` is written atomically (`textfile.atomic_write`, `jsonstore.dump_json`).
- Tests write only to temp folders: `OBJECT_STATE_DIR` is a temp folder (conftest's autouse fixture), and nothing writes to `~/.claude` or the real state dir. The fake `claude` (`backend/tests/fake_claude.py`) stands in for the CLI. Fixtures are synthetic.
- Only Object and Claude Code are named in code, tests and strings.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

The inputs and failure modes the spec implies that no task's happy path exercises, most likely first. Each one's test is listed in its owning task.

1. **A run interrupted or queued when the space closes is never lost and never runs twice.**
   - Cases: a job is running when the space is switched or the app quits; several jobs are queued from a "Run all" catch-up when it closes; the computer sleeps through an occurrence while the app is open; a rule is turned off or deleted while its job waits.
   - What must hold:
     - the interrupted and queued occurrences come back as `pending`, so the catch-up asks on the next open;
     - nothing runs without an answer;
     - a turned-off or deleted rule's waiting job is logged `skipped`, not run;
     - a long run never blocks the scheduler tick or the `POST /automations/catch-up` request.
   - Tests: `test_m21_runner.py::test_stop_reowes_queued_and_running`, `::test_off_or_deleted_rule_is_skipped`, `::test_jobs_never_block_tick_or_answer` (T3); `scripts/m21_acceptance.py` check 6 (T7).
2. **A schedule run starts no learning review.**
   - The memory and skills counters reach their intervals during a schedule run (it uses many tools).
   - The run's purpose is `"schedule"`, which isn't in M18's `reviews.REVIEW_PURPOSES`, and it never goes through `/api/ai/chat`, so `ReviewRunner.after_turn` is never called. It starts no review and leaves the counters of every other chat unchanged.
   - Tests: `test_m21_runner.py::test_schedule_run_skips_reviews` (T3, with M18's `ReviewRunner.after_turn` patched to record calls).
3. **The curator's protection is right across spaces.**
   - A skill used only by a schedule in a space that isn't open is protected. So is a skill named in a schedule's prompt that has never run (a yearly schedule).
   - A rule deleted in the open space drops its protection. A skill name that merely contains another one ("report" vs "weekly-report") doesn't count as a mention.
   - Tests: `test_m21_index.py::test_skills_in_use_across_spaces`, `::test_prompt_mentions_are_whole_names`, `::test_deleted_rule_unprotects` (T2).
4. **An agent can schedule only itself, only in the open space.**
   - `schedule_manage` must not read, change or delete another agent's schedule.
   - M17's `create_automation` tool must not make a `runAgent` rule; it could name any agent.
   - A proposal-mode run (read token) can list but not write.
   - A remote agent can't be scheduled.
   - Tests: `test_m21_schedule_tool.py::test_other_agents_schedules_are_404`, `::test_create_automation_refuses_run_agent`, `::test_read_token_cannot_write` (T4); `test_m21_model.py::test_remote_agent_refused` (T2).
5. **No write on read, and old versions stay safe.**
   - Opening a space that has agent schedules writes no space file. It writes `agent-schedules.json` only when its content differs.
   - A rule file with a `runAgent` action, read by an Object without M21, lists read-only and never runs. That already holds, because M14's model forbids unknown action kinds; the test pins it.
   - Unknown keys in a schedule's rule file survive a dialog save.
   - A run's space changes are exactly the AI Chat object plus what the agent's own tools wrote.
   - Tests: `test_m21_runner.py::test_open_writes_nothing` (T3); `test_m21_model.py::test_unknown_action_kind_stays_read_only` and `::test_unknown_keys_kept` (T2); `scripts/m21_acceptance.py` check 9 (T7).

### The `runAgent` action (`backend/objectapp/automations_model.py`; `RunAgentAction` in `frontend/src/api/types.ts`)

```jsonc
{
  "schemaVersion": 1,
  "name": "Weekly review",                 // M14's rule name rules (1-100 characters); shown as the schedule's name
  "description": "",
  "enabled": true,
  "trigger": { "kind": "schedule", "repeat": "every week on monday", "time": "09:00", "start": "2026-11-09" },
  "conditions": { "type": "filterGroup", "operator": "and", "elements": [] },
  "actions": [
    { "kind": "runAgent",
      "agentId": "01JC7ZK3T9Q4M2X8B5N6R1V0WE",   // M17 AGENT_ID ("assistant" or a ULID)
      "prompt": "Review last week's notes ({date:YYYY-MM-DD}) and list open tasks.",
      "model": null }                            // null: the agent's default (M16 clean_model rule otherwise)
  ],
  "templateRepeat": null,
  "createdAt": "2026-11-05T09:00:00.000Z"
}
```

```python
# automations_model.py (T1)
MAX_PROMPT = 20_000                         # our choice
# AGENT_ID: imported from agentmodel (M17), not copied

class RunAgentAction(_Strict):
    kind: Literal["runAgent"]
    agentId: str                             # fullmatch agentmodel.AGENT_ID
    prompt: str                              # stripped; 1..MAX_PROMPT characters
    model: str | None = None                 # aimodels.clean_model; ValueError -> aimodels.BAD_MODEL ("That isn't a model name.")

# The Action union and ACTION_KINDS gain "runAgent" at the END, so OBJECT_ACTION_KINDS = frozenset(ACTION_KINDS[:6]) is unchanged.
AGENT_ACTION_KINDS = frozenset({"runAgent"})
def agent_action(rule: AutomationRule) -> RunAgentAction | None    # the rule's runAgent action, or None
```

Shape rules, checked in `AutomationRule._shape`. Each raises with its message, which reaches the client as the 422 (our strings):

- A rule with a `runAgent` action has a `schedule` trigger: "An agent schedule runs on a schedule."
- It has exactly one action: "An agent schedule has exactly one action."
- `templateRepeat` is null: "An agent schedule can't repeat a template."
- An empty prompt: "A schedule needs a prompt."
- A prompt over `MAX_PROMPT`: "The prompt is too long (at most 20,000 characters)."

Checks against the machine, in `automations._check_against_space` (only when M14 checks against the space; a switch-only save skips them, as M14 does):

- `AgentRegistry().get(agentId)` must exist: otherwise "That agent isn't listed any more." (`agents.NOT_LISTED`; `get` raises `AgentNotFound` with it).
- A `kind: "remote"` agent (M20; `AgentRecord.kind == remotemodel.REMOTE_KIND`) is refused: "Schedules run Object's own agents, not remote ones."

**Placeholders.** `{date:FMT}` in `prompt` expands with M14's `expand_placeholders` against the run instant, which is the occurrence instant, also for catch-up runs. `{title}` and `{link}` expand to `""`, since there is no triggering object.

**What older versions do.** An Object without M21 fails validation on the unknown action kind. It lists the rule with `readOnlyReason`, never runs it and never rewrites it (M14 rule). Nothing to build; T2 pins the mechanism with a test.

### Running a schedule (`backend/objectapp/schedulerun.py`)

```python
STOPPED = "Stopped because the space was closed."           # our strings
HIDDEN = "AI features are hidden (Settings > AI Assistant)."  # = api_ai's 403 text
NO_URL = "Object's address isn't known yet."
SAVED = "Saved the chat."
NOTIFY_CHARS = 200
SCHEDULE_GUIDANCE = ("This chat was started by a schedule. No one is watching it live, so don't ask "
                     "questions: do the task, then give the result in your reply. It is saved as a note.")

@dataclass(frozen=True)
class AgentJob:
    rule_id: str
    instant: datetime          # the occurrence (UTC)
    catch_up: bool

@dataclass
class ScheduleResult:
    status: Literal["ok", "failed", "skipped"]
    path: str | None           # the AI Chat object's space path (ok only)
    detail: str | None         # SAVED, or the failure / skip message
    chat_id: str | None        # the transcript's chat id
    used_skills: list[str]

class AgentJobs:
    """One worker thread per open space; runs jobs one at a time, in the order they came due."""
    def __init__(self, engine: AutomationEngine, *, base_url: Callable[[], str | None],
                 registry: Callable[[], AgentRegistry] = AgentRegistry) -> None
    def start(self) -> None
    def submit(self, job: AgentJob) -> bool          # False when the same (rule_id, instant) is queued or running
    def pending(self) -> int                          # queued + running
    def wait_idle(self, timeout: float) -> bool       # test hook
    def stop(self, timeout: float = 5.0) -> None
        # queued jobs: back to their rules' pending (engine.scheduler.owe); the running one: its CLI is killed
        # (closing ai.run_turn), logged failed with STOPPED, and its occurrence owed too.

def run_schedule(space: Space, rule_id: str, name: str, action: RunAgentAction, instant: datetime, catch_up: bool, *,
                 registry: AgentRegistry, settings: dict[str, Any], base_url: str | None, notifier: Notifier,
                 announce: Callable[[ChangeEvent], None], cancel: threading.Event) -> ScheduleResult
def chat_title(name: str, instant: datetime, tz: Any) -> str
PURPOSE_FOR: Callable[[Space, str], str] = lambda space, rule_id: "schedule"
    # the run's RunScope purpose for a rule, read at call time; M24 sets it so its Desk sync rule runs as "work-sync"
    # f"{name} {local day YYYY-MM-DD}", the name cut so the whole fits aichat.TITLE_MAX
```

`run_schedule` runs these steps in order. Any failure stops it with `status: "failed"` and its message:

1. Refuse to start in these cases:
   - `settings["aiHidden"]`: fail with `HIDDEN`;
   - no `claude` (`ai.find_claude(settings.get("claudePath"))`): fail with `ai.NOT_FOUND` (`run_chat` would also raise `RunRefused(ai.NOT_FOUND)`);
   - no `base_url`: fail with `NO_URL`;
   - the agent is unknown, missing or read-only: fail with M17's messages (`agents.NOT_LISTED`, `api_ai.MISSING_FOLDER` "This agent's folder is missing: {path}", its `read_only_reason`);
   The default agent's folder is made by `ensure_default` (its first write) inside `run_chat`, as M17's chat route does.
2. The prompt is `expand_placeholders(action.prompt, space, None, None, instant)`. The model is `aimodels.resolve_model(action.model, agents.effective_model(agent, settings))`.
3. Run the chat with M20's `headless.run_chat(agent, settings=settings, space_root=space.root, space_name=space.name, space_key=appstate.space_key(space.root), api_url=base_url, prompt=prompt, title=chat_title(...), purpose=PURPOSE_FOR(space, rule_id) (`"schedule"` unless a later milestone sets the hook), model=model, timeout=ai.TURN_TIMEOUT, header={"schedule": {"ruleId", "name", "scheduledFor": iso, "catchUp"}}, stop=<async: cancel.is_set()>, announce=announce)`, in `asyncio.run` on the worker thread. `run_chat`'s first parameter is the `AgentRecord` (`target`); it passes `header`'s keys to `transcripts.start` as keywords, so `start` gains `schedule=`; its `stop` is `Callable[[], Awaitable[bool]]`, polled every `headless.STOP_POLL` s. It returns a `HeadlessResult` (`chat_id`, `state` `done`/`error`/`stopped`, `text`, `session_id`, `model`, `error`, `tool_lines`).
   - `run_chat` writes the header and the user line, makes the read-write turn token (`purpose="schedule"`), builds the `RunScope` (`write=True`, `purpose="schedule"`) and the `ai.Turn`, runs `ai.run_turn`, appends the tool lines and the assistant (or error) line, announces `agentChats`, and drops the token.
   - `cancel` set closes the run, which kills the CLI's process tree (M10); the result's state is then `"stopped"`.
   - `agentrun.RunRefused` (a nesting problem, no `claude`, or a default agent folder that can't be made) fails with its message.
4. When the result's state is `done`:
    - `aichat.create_chat_object(space, title=chat_title(...), messages=[user, assistant], context_refs=[], session_id=<sessionId>, agent_name=agent.name, origin=f"api:{agent.name}", announce=announce)`;
    - append the transcript's `object` line (`{"type": "object", "path", "at"}`, as `api_ai`'s `record_object` writes) and announce `agentChats`;
    - result `ok`, with `path` and `SAVED`.
5. Send the notification, only while `reminders_enabled(space.root)`:
    - through `notifier.send(title, body)` (M14's `Notifier`);
    - on `ok`: title the rule's name, body the reply's first `NOTIFY_CHARS` characters with whitespace collapsed;
    - on `failed`: body `"Failed: <message>"`;
    - none on `skipped`.
6. `used_skills` comes from the result's `tool_lines` (each `{"type": "tool", "id", "name", "input", "result", "isError", "at"}`):
    - the input `skill` (else `name`, else `command`) of each `Skill` call;
    - the `name` of each `mcp__object-agent__skill_view` call.

A contributor, `agentrun.add_contributor("schedule-guidance", 55, fn)` (order 55 in M17's registry of contributor orders; 50 is `guidance`, 60 `tools`, and 55 is free), appends `SCHEDULE_GUIDANCE` to `parts.append_prompt` when `scope.purpose == "schedule"`. It is registered by `schedulerun.install()` (idempotent), which `create_app` calls beside `learnhooks.install()`, `mcpgateway.install()` and `delegation.install()`, as M18-M20 register theirs.

### The engine's side (`backend/objectapp/automations.py`)

- `AutomationEngine.__init__(space, announce, notifier, interval=30.0)` gains the keyword `base_url: Callable[[], str | None] = lambda: None` and makes `self.agent_jobs = AgentJobs(self, base_url=base_url)`. `start`/`stop` start and stop it: `stop` stops the scheduler first, then `agent_jobs` (which owes what it couldn't run), then M14's worker.
- `run_scheduled(lr, instant, catch_up) -> dict | None`. For a rule with a `runAgent` action it calls `agent_jobs.submit(AgentJob(lr.id, instant, catch_up))` and returns None. Other rules run as before (`_execute(..., flush=True)`). `AutomationScheduler.tick` and `answer` leave the Nones out of the runs they return.
- `AutomationScheduler.answer_counted(rule_id, choice) -> tuple[list[dict], int]` is today's `answer` body returning `(runs, queued)`, where `queued` counts the occurrences handed to the agent jobs; `answer(rule_id, choice)` returns its `runs`, so its callers are unchanged. A `skip` answer still logs M14's `log_skipped_catch_up` run.
- `POST /api/automations/catch-up` (`api_automations.post_catch_up`) calls `answer_counted` and answers `{runs, queued}`. The client ignores `queued`.
- `execute_agent_job(job, cancel) -> dict` (the logged `AutomationRun`):
  - re-reads the rule; one that is gone, turned off or read-only is logged `skipped` with M14's `TURNED_OFF` or its read-only reason;
  - otherwise it calls `run_schedule` inside `writeorigin.acting_as(origin_for(rule_id))`;
  - it logs one run with one action result `{index: 0, kind: "runAgent", status, path, detail}` (flush) and calls `ScheduleIndex.record_used(...)`.
- `AutomationScheduler.owe(rule_id: str, instants: list[datetime]) -> None` merges the instants into the rule's `pending` with M14's `_merge_pending(entry, found, capped)` (`MAX_PENDING`, the 50 newest) under the scheduler's `_lock`, saves (`_save`), and calls `engine.announce_catch_up()` (`automationRuns`/`catch-up`). A rule with no state entry (turned off meanwhile) owes nothing.
- `catch_up_items` is unchanged. An agent schedule's row is M14's `CatchUpDialog` text `Run “{name}” for the {count} missed times?` (`createsObjects` false; `catch_up_name` is the rule's name).
- `rules_changed()` and `start()` also call `ScheduleIndex().sync_space(space.root, space.name, self.rules.all())` (below).

**Agent writes during a run** carry origin `api:<agent name>`, not `automation:`. They trigger other rules as any API write does (our call: the agent acts as a user would). A `runAgent` rule has a schedule trigger, so no write can trigger one: there is no loop.

**The app's own URL** (`base_url`):

- `create_app` gains `base_url: str | None = None`; `__main__.build_server_config` passes `f"http://127.0.0.1:{port}"`.
- `create_app(space, static_dir=None, watch=True, on_switch=None, base_url=None)`: the new keyword goes last. When it is None (tests with `TestClient`), `base_url()` answers M18's `idle.base_url` (`app.state.idle`: the `IdleClock`'s last request base URL seen, from `curator._base_url`). M18 has no `create_app(base_url=)` of its own; M21 adds it. `create_app` builds the `IdleClock` before the `AutomationEngine`, so the engine's `base_url` callable can read it.

### The transcript header (`backend/objectapp/transcripts.py`, M17's file; T3)

```python
INDEX_FILE = "agent-schedules.json"; MAX_USED = 100
def is_agent_schedule(rule: AutomationRule | None) -> bool
class ScheduleIndex:
    def __init__(self, state: Path | None = None) -> None
    def sync_space(self, space_root: Path, space_name: str, rules: Iterable[LoadedRule]) -> bool
        # replaces that space's entries with its readable runAgent rules (enabled or not), keeping each
        # entry's usedSkills; a read-only rule file keeps its old entry; writes only when the content differs,
        # never creates the file when it would hold nothing. Returns whether it wrote.
    def record_used(self, space_root: Path, rule_id: str, skills: Iterable[str]) -> None
    def entries(self, agent_id: str) -> list[dict[str, Any]]            # every space's, for this agent
class IndexUnreadable(Exception): ...
def skills_in_use(folder: Path) -> set[str]       # M18's agentskills.SCHEDULE_SKILLS
    # the agent is the one whose .object-agent/agent.json id is in `folder` (agentfiles.read_agent_file -> (data, revision));
    # usedSkills of the agent's entries, plus each current skill of the agent (directory names under
    # <folder>/.claude/skills/) named in an entry's prompt: case-insensitive, whole name
```

- Protection holds while a schedule exists, on or off (our call). A space's entries are refreshed only when that space is open. A space never opened again keeps protecting its skills (conservative, our call).

All the routes use `v1guard.agent_auth(guard, AgentRegistry(), request)` with `guard = V1Guard(ctx, TokenStore(ctx.space.root))` and `@guarded`, so they act only for the token's agent and only in the token's space, as M18's `api_learning_v1` and M20's `api_agent_a2a_v1` do. |---|---|---|---|
| `GET /api/v1/agent/schedules` | | `{schedules: ScheduleV1[]}`: this agent's, by name (casefold), then id | 403 not an agent's token |

## Our calls

1. **A schedule is an M14 rule** (a `schedule` trigger plus a new `runAgent` action), not a rule kind of its own. The spec asks for M14's scheduler, catch-up rules and storage. As a rule it gets each of these unchanged:
   - the state file, the "nothing missed runs without an answer" logic, the 50 cap and the 10-minute sleep gap;
   - the run log, the Trash, revision checks, the watcher, the events and Settings > Automations.
   Its own kind would mean a second store and a second scheduler with the same rules. Older versions read the new action kind as read-only and never run it.
2. An agent schedule has exactly one action, no conditions and no template repeat, as a template repeat is a fixed shape. `runAgent` is never offered in the rule editor's "+ Add action" menu: schedules are made on the agent page, in Settings through the same dialog, or by the agent's tool.
3. Agent runs don't run on M14's scheduler thread or in the catch-up request. They go to a per-space queue that runs one job at a time, in the order they came due, so a run of up to 5 minutes never delays other rules or the UI.
4. Closing the space (switch or quit) kills a running schedule and logs it failed with "Stopped because the space was closed.". The interrupted occurrence, and any queued ones, go back to `pending`, so the catch-up asks on the next open. Nothing is lost and nothing runs without an answer.
5. Each occurrence is a **new chat**. It runs at most 300 s (M10's `TURN_TIMEOUT`), with write tools and the agent's own switches, and with a short appended note that no one is watching (`SCHEDULE_GUIDANCE`).
6. The result is always saved as an AI Chat object titled "<schedule name> <YYYY-MM-DD>" (the occurrence's local day). A failed run saves no AI Chat; its transcript, run log line and "Failed: …" notification tell what happened.
7. The notification obeys "Activate notifications", as M14's `notify` does. Its body is the reply's first 200 characters.
8. `{date:FMT}` works in a schedule's prompt and uses the occurrence's instant, so a missed Monday run is dated Monday.
9. An optional per-schedule model (`model`, null = the agent's default), set with M16's picker. It is the chat header's override, kept with the schedule.
10. A schedule runs only Object's own local agents. Remote agents (M20) are refused.
11. With "Hide AI features" on, a due schedule doesn't run: it is logged failed with the 403's text.
12. Agents schedule only themselves: `schedule_manage` acts on the token's agent in the token's space, and M17's `create_automation` refuses `runAgent` rules.
13. A run's tool writes count as the agent's (`api:<agent name>`), so they may trigger ordinary M14 rules. No write can trigger a `runAgent` rule, so there is no loop.
14. **Skills a schedule uses** are those its runs loaded (`Skill` calls and `skill_view`), plus the agent's skills named in its prompt as a whole name. Prompt names cover a schedule that hasn't run yet, such as a yearly one.
15. Those skills are kept in a machine-wide index in the state dir. The curator can then protect skills of schedules in spaces that aren't open.
16. Protection holds while a schedule exists, on or off. A space's entries are refreshed whenever it opens, and a space never opened again keeps its entries. An unreadable index makes the curator leave that agent alone.
17. The two M18 hooks are `reviews.REVIEW_PURPOSES` (which leaves out `"schedule"`) and `agentskills.SCHEDULE_SKILLS`. "Learn from this chat" on a schedule's chat is still allowed: Gene asks for it, which isn't a background review.
18. Agent schedules appear in Settings > Automations as rows saying which agent they run; Edit opens the schedule dialog. The agent page's tab is "Schedules", the last one (order 80). It shows the open space's schedules only.
19. The app learns its own loopback URL from `build_server_config`, or in tests from M18's `IdleClock.base_url` (the last loopback request).
